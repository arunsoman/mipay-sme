# Local Deployment DNS and Certificate Explanation

## How admin.afriqpay.com Resolves to Local

### 1. DNS Resolution Flow

When you access `admin.afriqpay.com` locally, the resolution happens in this order:

#### A. /etc/hosts (First and Most Common)
On your local machine (where you're running Docker), add an entry:

```bash
# In /etc/hosts (Linux/Mac) or C:\Windows\System32\drivers\etc\hosts (Windows)
13.61.207.80  admin.afriqpay.com mipay.afriqpay.com
# OR for localhost-only:
127.0.0.1  admin.afriqpay.com mipay.afriqpay.com
```

**How it works:**
- When your browser resolves `admin.afriqpay.com`, it first checks `/etc/hosts`
- If found, it resolves to the specified IP immediately
- DNS queries are never sent externally
- This bypasses the need for actual domain registration

#### B. Docker Network DNS (Internal)
When Docker Compose creates the `sme-mesh` network, containers can resolve each other by service name:

```yaml
# In docker-compose.yml networks section
networks:
  sme-mesh:
    external: true
```

Containers on the `sme-mesh` network can resolve:
- `gateway` → `127.0.0.1` (published port)
- `idp` → Internal Docker IP
- `rbac` → Internal Docker IP
- `backend` → Internal Docker IP

But **external** names like `admin.afriqpay.com` require `/etc/hosts` entry.

#### B. Public DNS (Production)
In production, `admin.afriqpay.com` is a real domain:
- Registered via a DNS registrar (Nic.Africa, GoDaddy, etc.)
- DNS A record points to the server's public IP
- Let's Encrypt certificates are automatically issued
- NGINX on the host serves HTTPS

## How Certificates Work Locally

### 2. Certificate Hierology for Local Development

There are **three certificate scenarios** depending on your setup:

#### Scenario A: Production with Let's Encrypt (afriqpay host)
```
┌──────────────────────────────────────────────────────────────┐
│  Your Server (13.61.207.80)                                  │
│  └──✅ Let's Encrypt Certificates                              │
│       /etc/letsencrypt/live/admin.afriqpay.com/             │
│       ├── fullchain.pem  (public cert + intermediate)        │
│       └── privkey.pem      (private key)                     │
│                                                                │
│  NGINX on host terminates TLS                                │
│  Certs auto-renewed every 90 days                            │
└──────────────────────────────────────────────────────────────┘
```

**How it works in the afriqpy setup:**
- NGINX on the host (`/etc/nginx/`) has real Let's Encrypt certs
- `admin.afriqpay.com` resolves to the host's public IP (13.61.207.80)
- External users access via `https://admin.afriqpay.com`
- Certificates are valid and trusted (public CA)

#### Scenario B: Local Development with Self-Signed Certs
```
┌──────────────────────────────────────────────────────────────┐
│  Your Laptop                                                   │
│  └──🔧 Self-Signed Certificates                               │
│       generated by:                                          │
│       openssl req -x509 -newkey rsa:2048 -keyout key.pem   │
│           -out cert.pem -days 365 -nodes                      │
│                                                                │
│  Add to trust store:                                          │
│  security add-trusted-cert -f /tmp/cert.pem                   │
└──────────────────────────────────────────────────────────────┘
```

**How to use:**
1. Generate self-signed certs
2. Place them somewhere accessible
3. Update NGINX config to use your certs
4. Add `admin.afriqpay.com` to `/etc/hosts` pointing to `127.0.0.1` or Docker host IP
5. **Browser warning**: You'll see "Your connection is not private"
6. **Fix**: Add the cert to your OS trust store

#### Scenario C: Trustplane Internal PKI (Recommended for Dev)
```
┌──────────────────────────────────────────────────────────────┐
│  Trustplane Docker Setup                                       │
│  └──🔐 Internal CA + Service Certs                            │
│                                                                │
│  pki-init container generates:                                │
│  ├── /pki/platform-ca.pem        (root CA)                   │
│  ├── /pki/idp-server.pem         (IdP server cert)           │
│  ├── /pki/idp-server-key.pem     (IdP key)                  │
│  └── /pki/export-backend.sh      (exports to backend)       │
│                                                                │
│  Gateway uses internal CA:                                    │
│  proxy_ssl_verify off            (skip mTLS verification)      │
│  proxy_ssl_name portal.fapi.local                            │
│  proxy_ssl_cert /pki/gateway-cert.pem                        │
│  proxy_ssl_key /pki/gateway-key.pem                          │
│  proxy_ssl_client_cert /pki/platform-ca.pem                   │
└──────────────────────────────────────────────────────────────┘
```

**How it works in trustplane:**
- `pki-init` container runs on first startup
- Generates a private CA and service certificates
- Certificates are mounted to `/pki/` volume
- All trustplane services (gateway, idp, rbac, comms) use these certs
- `proxy_ssl_verify off` in NGINX means the loopback hop skips mTLS verification
- The gateway's internal CA cert is used for mTLS between gateway and upstreams

**To use trustplane PKI locally:**
```bash
# The pki-init container handles this automatically
# Certs are at ./deploy/pki/ after setup

# Trust the CA once:
sudo security add-trusted-cert -f /usr/local/share/trustanchors /pki/platform-ca.pem
sudo security cert -add -f /pki/platform-ca.pem
```

## 3. Local Development Setup Options

### Option 1: Let's Encrypt + /etc/hosts (Closest to Production)
```bash
# 1. Add to /etc/hosts
echo "127.0.0.1 admin.afriqpay.com mipay.afriqpay.com" >> /etc/hosts

# 2. Generate self-signed certs or use existing
mkdir -p /etc/nginx/ssl
openssl req -x509 -newkey rsa:2048 -keyout /etc/nginx/ssl/admin.afriqpay.com.key \
    -out /etc/nginx/ssl/admin.afriqpay.com.crt -days 365 -nodes -subj "/CN=admin.afriqpay.com"

# 3. Update nginx config to use your certs
#    ssl_certificate     /etc/nginx/ssl/admin.afriqpay.com.crt;
#    ssl_certificate_key /etc/nginx/ssl/admin.afriqpay.com.key;

# 4. Run docker compose
cd /home/arun/sme/trustplane && docker compose up -d --build
cd /home/arun/sme/deploy/afriqpay && docker compose up -d --build

# 5. Browse to https://admin.afriqpay.com
#    Browser may show warning → click "Advanced" → "Proceed"
```

### Option 2: Trustplane Internal PKI (No Browser Warnings After Trust)
```bash
# 1. Start trustplane (pki-init generates certs automatically)
cd /home/arun/sme/trustplane && docker compose up -d --build

# 2. Wait for pki-init to complete (check logs: docker compose logs pki-init)

# 3. Trust the CA on your OS
#    macOS:
sudo security add-trusted-cert -d -r trustSettings -k /Library/Keychains/System.keychain /pki/platform-ca.pem

#    Linux (Ubuntu):
sudo cp /pki/platform-ca.pem /usr/local/share/ca-certificates/
sudo update-ca-certificates

#    Windows:
#    Double-click the .cer file → "Install Certificate" → "Local Machine" → "Place all certificates in the following store" → "Trusted Root Certification Authorities"

# 3. Add hosts entry (if not using Docker DNS)
echo "127.0.0.1 admin.afriqpay.com" >> /etc/hosts

# 4. Now browse with no warnings!
#    https://admin.afriqpay.com works perfectly
```

### Option 3: Production (afriqpay host) - No Local Changes Needed
```bash
# Just start the services - they already have certs
cd /home/arun/sme/deploy/afriqpay && docker compose up -d --build

# The host already has:
# /etc/letsencrypt/live/admin.afriqpay.com/fullchain.pem
# /etc/letsencrypt/live/admin.afriqpay.com/privkey.pem

# DNS: admin.afriqpay.com → 13.61.207.80 (already configured on host)
# HTTPS: Works immediately for external users
```

## 4. Gateway TLS Configuration Details

The trustplane gateway (`bff.go`) has this important TLS configuration:

```go
// In server.go - gateway listen configuration
srv := &http.Server{
    Handler:           http.HandlerFunc(g.serve),
    ReadHeaderTimeout: 5 * time.Second,
    ReadTimeout:       30 * time.Second,
    WriteTimeout:      60 * time.Second,
    IdleTimeout:       120 * time.Second,
    MaxHeaderBytes:    cfg.Server.MaxHeaderBytes,
    TLSConfig:         tlsCfg,  // From mtlsx.ServerConfig
}
```

And the NGINX config proxies to it:
```nginx
# NGINX listens on 127.0.0.1:19120
# Terminates public TLS, forwards to gateway internally
server {
    listen 443 ssl;
    server_name portal.fapi.local;
    proxy_pass https://127.0.0.1:19120;
    proxy_ssl_server_name on;
    proxy_ssl_name portal.fapi.local;
    proxy_ssl_verify off;  # Skip mTLS verification on loopback hop
    ...
}
```

**Key Points:**
- `proxy_ssl_verify off` - Allows the loopback connection without mTLS verification
- This is safe because the gateway→NGINX hop is on localhost only
- The external TLS is terminated by the host's NGINX (with real certs)
- The internal gateway→upstream connection uses trustplane's internal PKI

## 4. Summary: Which Certificate Scenario to Use

| Scenario | Use Case | Browser Warning | Setup Complexity |
|----------|----------|----------------|------------------|
| **Let's Encrypt + /etc/hosts** | Production-like local dev | Yes (self-signed) | Low |
| **Trustplane Internal PKI** | Full dev with no warnings | No (after trust CA) | Medium |
| **Production (afriqpy host)** | Testing against real env | No | Low (just `docker compose up`) |

**Recommendation for Local Development:**
Use **Option 2 (Trustplane Internal PKI)** - it generates proper certs, and after trusting the CA once, you get no browser warnings. This is the most sustainable approach for FAPI 2.0 development.

**For Production Testing:**
Use **Option 3** - just start the afriqpay stack and test against the real deployed environment at `13.61.207.80`.
